## 결론: **인수 반려**

업체 보고서는 "치명적 결함 0건"이라고 했지만, 직접 돌려본 결과는 달랐다.

- 형식이 깨진 패킷 하나, 또는 두 조각으로 나뉘어 온 정상 패킷 하나로 **서버 프로세스가 통째로 종료**된다 (A1, A2).

아래 8건을 고친 뒤 같은 시나리오로 다시 돌려 모두 정상 동작을 확인했다.

## Part A — 고칠 곳

모든 캡처는 시나리오 직전에 서버를 재시작해서 통계가 0부터 시작하도록 했다.

### A1. 형식이 깨진 패킷 하나로 서버 프로세스 전체가 종료된다

**재현**
1. OutsourcedServer 실행
2. LoadTester → 4 (Type 필드 없는 JSON 전송)
3. 서버 창이 종료된다

**증거**
- 수정 전: `증거/A_before_4비정상.png` — `Unhandled exception. RuntimeBinderException: Cannot convert null to 'int'` … `ClientSession.cs:line 73`, 이후 프로세스 종료. LoadTester는 "응답 없음".
- 수정 후: `증거/A_after_4비정상.png` — `[경고] ID:1 Type 필드가 없는 패킷을 버립니다`, 서버는 계속 동작하고 다음 정상 채팅 `아직 살아있나요?`의 응답이 돌아온다.

**원인**
- `ClientSession.cs` 73행 `int type = (int)packet.Type;` — Type이 없으면 null을 int로 바꾸다 예외가 난다.
- 근본 원인은 `ClientSession.cs` 68행 `private async void HandlePacket`. async void에서 난 예외는 호출한 쪽으로 돌아오지 못하고 스레드풀에서 그대로 터진다. 그래서 `Program.cs`의 `try/catch`(`[서버 종료]` 출력)도 거치지 않고 프로세스가 죽었다. 스택 트레이스 끝의 `Task.<>c.<ThrowAsync>` … `ThreadPoolWorkQueue.Dispatch`가 그 흔적이다.
- 결과적으로 접속자 한 명이 보낸 이상한 패킷 하나에 모든 플레이어가 튕긴다.

**고친 코드** (커밋 `85d4e98`)
```csharp
// before
HandlePacket(json);                                  // RunAsync 안
private async void HandlePacket(string json) { ... int type = (int)packet.Type; ... }

// after
try { await HandlePacketAsync(json); }               // RunAsync 안
catch (Exception ex) { Console.WriteLine($"[경고] ID:{PlayerId} 잘못된 패킷을 버립니다 : ..."); }

private async Task HandlePacketAsync(string json)
{
    dynamic? packet = JsonConvert.DeserializeObject(json);
    if (packet == null) return;
    if (packet.Type == null) { Console.WriteLine("[경고] ... Type 필드가 없는 패킷을 버립니다"); return; }
    int type = (int)packet.Type;
    ...
}
```

### A2. 패킷이 두 조각으로 나뉘어 오면 서버가 종료된다

**재현**
1. OutsourcedServer 실행
2. LoadTester → 2 (본문 55바이트를 27 + 28로 나눠 50ms 간격 전송)

**증거**
- 수정 전: `증거/A_before_2분할(1).png`, `(2).png` — 서버 `JsonReaderException: Unterminated string. Expected delimiter: ". Path 'Message', line 1, position 55` (`ClientSession.cs:line 70`) 후 종료. LoadTester는 `Broken pipe`, "아무것도 안 돌아왔습니다".
- 수정 후: `증거/A_after_2분할.png` — 서버 생존, `AAAA-분할전송-테스트-BBBB`, `정상패킷-그다음` 두 채팅이 온전히 돌아온다.

**원인**
- `PacketHelper.cs` 51행(헤더), 63행(본문) — `socket.Receive(body, 0, bodyLength, …)`를 **한 번만** 호출한다.
- `Receive`는 "최대 bodyLength 바이트"를 읽을 뿐, 다 올 때까지 기다리지 않는다. 앞 조각 27바이트만 도착한 시점에 반환되고, 나머지 28바이트는 0으로 빈 채 JSON 파싱으로 넘어갔다. 에러 위치가 본문 끝인 `position 55`인 것과 정확히 맞는다.
- 예외는 A1과 같은 async void 경로로 프로세스를 종료시켰다.

**고친 코드** (커밋 `c16b8c6`, 이후 `f89189c`에서 비동기화)
```csharp
// before
int n = await Task.Run(() => socket.Receive(header, 0, 4, SocketFlags.None));
await Task.Run(() => socket.Receive(body, 0, bodyLength, SocketFlags.None));

// after
if (!await ReadExactAsync(socket, header, 4)) return null;
if (!await ReadExactAsync(socket, body, bodyLength)) return null;

private static async Task<bool> ReadExactAsync(Socket socket, byte[] buffer, int size)
{
    int read = 0;
    while (read < size)
    {
        int n = await socket.ReceiveAsync(new ArraySegment<byte>(buffer, read, size - read), SocketFlags.None);
        if (n == 0) return false;
        read += n;
    }
    return true;
}
```

> 참고: LoadTester 3번(버스트 100개)은 수정 전에도 보낸 100 / 돌아온 100으로 정상이었다 (`증거/A_before_3버스트.png`). 데이터가 이미 한꺼번에 도착해 있으면 Receive가 한 번에 다 읽어서 드러나지 않은 것으로 보고, 별도 결함으로 보고하지 않는다.

### A3. UDP 좌표가 보낸 적 없는 값으로 깨진다

**재현**
1. OutsourcedServer 실행
2. LoadTester → 6 (접속 → `MOVE|id|i|회차×3|i` 10개 → 종료를 5회 반복)
3. 각 회차 STATE의 y 값을 확인한다 (LoadTester는 y를 1~10만 보낸다)

**증거**
- 수정 전: `증거/A_before_6재접속.png` — 2회 실행 모두 보낸 적 없는 y가 나왔다.

  | 회차 | 1 | 2 | 3 | 4 | 5 |
  |---|---|---|---|---|---|
  | 1차 실행 y | 1 | **210** | **110** | 10 | **210** |
  | 2차 실행 y | 1 | **210** | **110** | **20** | **110** |

  전부 초록색 "STATE에 내가 있음"이고, 서버 UDP적용도 50(=5×10)으로 개수는 정상이다. 개수만 세는 통계로는 드러나지 않는 버그다.
- 수정 후: `증거/A_after_6재접속.png` — y = 2, 1, 2, 1, 2로 모두 보낸 범위(1~10) 안이다.

**원인**
- `UdpServer.cs` 80행 `string msg = Encoding.UTF8.GetString(buffer);` — 받은 바이트 수(`result.ReceivedBytes`)를 무시하고 1024바이트 버퍼 **전체**를 문자열로 바꾼다.
- 버퍼는 재사용되므로, 짧은 패킷 뒤에 이전 긴 패킷의 꼬리가 남는다.
  - 1회차 마지막 `MOVE|1|10|3|10` (14바이트)
  - 2회차 2번째 `MOVE|2|2|6|2` (12바이트) → 버퍼 `MOVE|2|2|6|2` + 남은 꼬리 `10` → **y = 210**
  - 110(`1`+`10`), 20(`2`+`0`)도 같은 방식으로 계산된다. 1회차만 정상인 이유는 버퍼가 아직 비어 있었기 때문이다.
- 회차마다 값이 달라지는 이유: LoadTester가 소켓에 쌓인 첫 STATE를 읽는데, 그 시점에 몇 번째 패킷까지 적용됐는지에 따라 붙는 꼬리가 달라진다.

**고친 코드** (커밋 `45021c6`)
```csharp
// before
string msg = Encoding.UTF8.GetString(buffer);
// after
string msg = Encoding.UTF8.GetString(buffer, 0, result.ReceivedBytes);
```

### A5. 남의 PlayerId를 적으면 남의 캐릭터를 움직일 수 있다

**재현**
1. OutsourcedServer 실행
2. LoadTester → 7 (BotA, BotB 접속 후 B가 자기 소켓으로 `MOVE|A의ID|9999|30|15` 전송)

**증거**
- 수정 전: `증거/A_before_7교차.png` — **UDP적용 3** = A 정상 1 + B 정상 1 + **B의 위조 1**.
  - LoadTester는 초록색 "A의 위치가 (5,5)에서 안 바뀌었습니다"를 출력했다. 하지만 받은 STATE가 `STATE|1,BotA,5,5`로 **BotB가 없다.** B가 등록되기도 전, 위조 패킷보다 0.4초 앞서 쌓인 첫 STATE를 읽은 것이므로 판정 근거가 될 수 없다. 서버 통계로 판단했다.
- 수정 후: `증거/A_after_7교차.png` — `[경고] 127.0.0.1:56261 에서 ID 1 를 사칭한 위치 패킷을 버립니다`. 56261은 바로 위 `BotB 주소 등록 : 127.0.0.1:56261`과 같은 포트다. **UDP적용 2**.

**원인**
- `UdpServer.cs` 115~137행 — 패킷 안의 PlayerId로 세션을 찾고, 보낸 주소가 그 세션에 등록된 주소인지 확인하지 않는다. 시퀀스를 9999로 크게 주면 시퀀스 검사도 통과한다.

**고친 코드** (커밋 `eb9d35a`)
```csharp
if (session.UdpEndPoint == null)
{
    session.UdpEndPoint = from;  ...
}
else if (!session.UdpEndPoint.Equals(from))          // 추가
{
    Console.WriteLine($"[경고] {from} 에서 ID {playerId} 를 사칭한 위치 패킷을 버립니다");

```
> 한계: 첫 패킷으로 주소를 등록하는 방식이라, 진짜 주인보다 먼저 위조 패킷이 오면 막지 못한다. 근본 대책은 WELCOME에 세션 토큰을 내려주고 UDP 패킷에 함께 싣는 것이다.

### 어느 구간부터 나빠지나

②에서 **10명은 전원 성공, 50명부터 실패 30건**이 나오고 최대 응답이 9003ms로 튄다. 실패한 봇은 WELCOME을 10초 가까이 기다리다 타임아웃됐다. 나빠지는 구간은 **10명과 50명 사이**이고, 내 PC의 스레드풀 최소 워커 수 **8**과 맞는다.

### 왜 거기서 나빠지나 — 코드의 어느 줄 때문인가

- **원인 줄**: `PacketHelper.cs` 51행, 63행 `await Task.Run(() => socket.Receive(...))`
- **접속자 한 명이 자원을 잡아먹는 방식**: `Receive`는 블로킹 함수다. 데이터가 올 때까지 그 스레드는 아무것도 못 하고 멈춰 있다. `Task.Run`으로 감싸면 그 멈춰 있는 일을 스레드풀 스레드가 맡는다. 접속자는 로그인 뒤에도 다음 패킷을 기다리며 계속 `Receive`에 걸려 있으므로, **접속자 1명 = 스레드풀 스레드 1개 상시 점유**가 된다.
- **8을 넘으면 갑자기 느려지는 이유**: 스레드풀은 최소치(8개)까지는 바로 스레드를 내준다. 그 이상은 새 스레드를 천천히 하나씩 추가한다. 9번째 접속자부터는 앞사람이 스레드를 놓아주지 않으니, 새 스레드가 생길 때까지 로그인 패킷을 처리하지 못하고 줄을 선다.
- **서버 통계 증거** (`증거/B_fix1_서버통계.png`, 50명 측정 중)

  ```
  t=133s | 접속 50 | 스레드  9
  t=135s | 접속 50 | 스레드 11
  t=137s | 접속 50 | 스레드 13
  t=139s | 접속 50 | 스레드 16
  t=141s | 접속 50 | 스레드 19
  ```
  접속 50명이 한 번에 들어왔는데 스레드는 2초에 2~3개씩만 는다. 50개가 될 때까지 기다리면 10초 타임아웃을 넘긴다.

  > 맥은 최대 워커가 32767이라 가용워커가 0까지 떨어지지는 않았다. 병목은 "상한"이 아니라 "새 스레드가 생기는 속도"였다.

### 고친 뒤 다시 측정

- 커밋 `f89189c`: `Task.Run(() => socket.Receive(...))` → `await socket.ReceiveAsync(...)`
- **고치면 왜 빨라지나**: `ReceiveAsync`는 OS에 "데이터 오면 알려줘"라고 등록만 하고 스레드를 바로 돌려준다. 기다리는 동안 스레드가 필요 없어서, 접속자 수와 스레드 수가 분리된다.
- **결과**: ③ 10~500명 **전부 실패 0**, 500명 최대 498.0ms (`증거/B_after_결과.png`).
  - 50명만 따로 측정 (15:41): 50 / 0, 최대 165.9ms. 서버 스레드는 8에서 그대로였다 (`증거/B_fix2_서버통계.png`).
  - 전체 측정 중 서버 통계 `접속 154 | 스레드 11` (`증거/B_after_서버통계.png`): 154명을 스레드 11개로 처리한다.

## Part C — 업체 검토서 판정

| # | 업체 의견 | 판정 | 근거 |
|---|---|---|---|
| 1 | TCP/UDP 분리 구조는 적절 | **동의** | 로그인·채팅은 유실되면 안 되니 TCP, 위치는 다음 틱(33ms)에 새 값이 오므로 재전송이 필요 없는 UDP가 맞다. |
| 2 | STATE를 한 패킷에 묶어 보내는 건 좋은 설계 | **동의** | 30Hz × N명에게 N명 위치를 따로 보내면 틱당 N²개, 묶으면 N개다. 접속자가 늘수록 차이가 커진다. |
| 3 | `_ = session.RunAsync()`는 await 누락 | **반대** | await를 붙이면 첫 접속자가 나갈 때까지 다음 Accept로 못 간다. 직접 해보니 10명 중 1명만 성공했다 (실행 증명 1). |
| 4 | 빈 catch는 안티패턴, 로그·재시도 추가 | **반대** | UDP 위치는 33ms 뒤 최신 값으로 다시 보내므로 재시도는 오래된 값을 보내는 것일 뿐이다. 로그를 찍으면 초당 30 × 접속자 수만큼 줄이 쌓여 통계 줄이 묻힌다. |
| 5 | Task.Delay(33)은 부정확, 고정밀 타이머로 교체 | **반대** | 30Hz 대비 30.3Hz는 1% 차이다. 클라이언트는 받은 최신 STATE만 그리므로 체감 차이가 없다. 고정밀 타이머·바쁜 대기는 CPU만 쓴다. |
| 6 | MAX_BODY 8192는 너무 작음, 65535로 | **반대** | 8192바이트는 한글 약 2,700자로 채팅에 충분하다. 상한은 악성 길이 헤더 방어용(`PacketHelper.cs` 주석)이라, 올리면 접속 하나로 64KB 버퍼 할당을 유도할 수 있다. TestClient도 8192를 기준으로 받는다. |
| 7 | Listen(512)는 과도한 자원 예약, 100으로 | **반대** | 백로그는 "Accept 대기 줄의 최대 길이"일 뿐 미리 잡는 메모리가 아니다. 동시 접속이 몰리는 순간(LoadTester 500명)을 버티는 용도다. 내 맥은 `somaxconn = 128`이라 512도 128로 제한되는데, 업체 권고 100은 그보다도 작다 (`증거/c_somaxconn.png`). |
| 8 | NoDelay = true는 대역폭 증가, 끄라 | **반대** | Nagle을 켜면 앞 패킷의 ACK가 올 때까지 작은 패킷을 모아 두므로 채팅·알림이 지연된다. 게임은 대역폭보다 지연이 중요하고, 패킷이 작고 드물어서 대역폭 증가는 미미하다. |
| 9 | StringBuilder 필드는 스레드 안전하지 않음 | **반대** | `_stateBuilder`는 `BroadcastLoopAsync` 하나에서만 쓰이고, 루프는 한 틱씩 순서대로 돈다. 동시 접근이 일어나지 않는다. 필드로 재사용하면 초당 30번의 할당이 줄어든다(의도된 개선). |
| 10 | 동시 접속 처리 문제없음, 부하 테스트 불필요 | **반대** | 수신이 `Task.Run` + 블로킹 Receive라 접속자마다 스레드를 붙잡는다. 직접 측정하니 50명에서 실패 30~46건이 났다 (실행 증명 2). |

### 실행 증명 1 — 의견 3 (await를 붙이면 동시 접속이 막힌다)

- **한 일**: 업체 권고대로 `GameServer.cs` 72행을 `await session.RunAsync();`로 바꾸고(커밋 `04c7c03`), 서버 재시작 후 LoadTester 1 → 10명 측정.
- **결과**: **성공 1 / 실패 9**. 서버 통계 **접속이 1에서 더 오르지 않음** (`증거/C_의견3_await실험.png`, CSV 16:02 행).
- **이유**: `await`는 RunAsync가 끝날 때까지 기다린다. RunAsync는 그 접속자가 나갈 때까지 끝나지 않으므로, 그동안 while 루프가 다음 `AcceptAsync`로 넘어가지 못한다. `_ =`는 누락이 아니라 의도된 fire-and-forget이고, 예외는 RunAsync 안의 try/catch/finally가 처리한다.
- 실험 후 되돌렸다 (커밋 `137337a`).

### 실행 증명 2 — 의견 10 (부하 테스트 없이 "문제없다"고 할 수 없다)

- **한 일**: 납품본 그대로 LoadTester 1번 측정 (Part B).
- **결과**: 원본 50명 **4 / 46**. A8만 고친 상태에서도 50명 **20 / 30**, 최대 9003ms. 측정 중 서버 통계 `접속 50 | 스레드 9 → 19`.
- **반박**: 업체는 "수신 처리를 비동기로 구현했으므로 막히지 않는다"고 했다. 하지만 `Task.Run`으로 감싼 블로킹 Receive는 비동기처럼 보일 뿐 스레드를 점유한다. 정적 분석만으로는 이게 드러나지 않았고, 부하 테스트를 하자마자 드러났다.
